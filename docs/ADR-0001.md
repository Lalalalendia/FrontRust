# ADR-0001 — Separate semantic model from DOM and Canvas renderers

Status: **provisional, implemented at PoC scale** (2026-10-25).

## Decision

A reusable Rust core owns typed commands, authoritative local demonstration state, undo and document revision. DOM and Canvas are presentation adapters over a single state instance compiled into WebAssembly.

A Rust SSR server owns public semantic content and metadata. The browser does not need to execute WASM for the initial `<h1>`, description, canonical, Open Graph and JSON-LD. In the PoC the reference server uses Rust `std` rather than a framework; Axum/Leptos adoption is a **separate architectural gate**, not a hidden dependency.

```
Browser: real semantic HTML/inputs --\
                                    \-> same rui-wasm -> rui-core state
Browser: Canvas event/draw ------/

Server: rui-server -> HTML/SEO markup; the JS adapter loads one wasm instance
```

## Invariants

- No second mutable object model in the renderer adapters.
- No-op commands do not change `document_revision` or `scene_revision`.
- Selection changes `scene_revision`, not `document_revision`.
- Geometry changes both revisions.
- DOM input and Canvas pointers command the same Rust model.
- HTML stays meaningful without WASM and the demo must NOT silently switch to a production JS state machine.
- A change of rendering backend must not change document identity, focus ownership or durable revision; that remains a next-stage acceptance gate.
- `rui-server` is a **loopback dev server**, not a public SSR service.

## Deliberately out of scope

- Native Masonry widget tree and real Masonry/WASM compilation.
- Production storage, auth, collaboration, security hardening.
- IME and text editing, screen readers, mobile interaction, full WCAG acceptance.
- PreparedText implementation or Rewatch DAG runtime.
- Dynamic SEO content model, sitemap lifecycle, i18n, crawler smoke tests.
- Native and browser pixel equivalence.

## Tradeoffs

The PoC uses browser API glue in JavaScript because DOM events and Canvas API remain browser-native interfaces. It does **not** duplicate business logic in JS. The test-only mock has matching API, but this is not proof of parity with Rust/WASM until native and wasm builds run on the same test vector.

An eventual Masonry adapter may render the UI shell, but it should not replace DOM forms/semantic content where the browser already supplies high-quality accessible controls. The default hypothesis is coexistence, not universal canvas-only widgets.
